> **与其它文档的关系**：
> [`000-工程规划.md`](000-工程规划.md) **§8.1** 是**规划期**的能力对齐矩阵（"预期一致"）；
> 本文是**as-built 复盘**（"现在实际是什么"），并对 §8.1 的每条给出**实测/源码级**判定。
> 两者冲突时**以本文为准**，并回头修订 §8.1。
> **参考基线**：`pi-desktop-hos` v0.12.1（`docs/鸿蒙环境能力清单-v0.12.1.md`，33 项主表 + REV-1/2/3）
> 及其 v0.11.1 前版（用户指定的参考文档）。两版冲突处按 hos 自己的口径**以 v0.12.1 为准**（REV-3.2 已逐条列出 14 处变化）。
> **证据口径**：✅ 实测（本轮或已入库的真机证据）｜🔶 沿用（有据但非本轮取证）｜⬜ 待验证（未取证，含源码级推断）｜⚠️ 受限 / 部分可用。
> **根因层**：**L1** 平台硬约束 ｜ **L2** 原生产物缺失 ｜ **L3** 本工程配置 ｜ **L4** 上游接口缺失（与 hos 能力清单同构，便于逐条对接）。

## 0. 判据与方法（先说清楚结论是怎么来的）

1. **基准集合**：取 `pi-desktop-hos/docs/鸿蒙环境能力清单-v0.12.1.md` **§A.2 的 33 项**做主表，
   再补 **5 项「清单外但 hos 有」** 的能力（导出、技能包、选择器 Tab、局域网访问、窗口状态）。
   这样做的原因：hos 的 33 项是**平台能力**口径，不含**壳独有功能**；"复刻能力"必须两者都算。
2. **判定方式**：以本仓库源码/产物为 as-built 证据（文件 + 行号见 §I），
   与 hos 的实测记录逐条对齐；ark 侧**未实测**的项一律记 ⬜，不按"应该一样"写成 ✅。
3. **本轮新增的源码级发现**（非实测，但可由代码直接判定）：见 §C.1「会话导出」——
   hos 的修复判据在 ark 上**不成立**，这是两工程运行时差异带来的新缺陷，不是"照抄补丁"能解决的。
4. **未做的验证**（诚实标注）：本文未上真机、未重跑构建、未执行任何导出请求。所有 ark 侧 ✅ 均**沿用已入库证据**
   （`docs/evidence/` 本地留存 + 提交 `fbc0035` 的对话验证 + `ohos-node-bridge/logs/20261016-1/`），
   凡属推断一律标 ⬜。

## A. 结构性差异（后面每一项的成因都在这里）

| 维度 | `pi-desktop-hos` v0.12.1 | `pi-desktop-ark` 当前 | 后果 |
|---|---|---|---|
| 运行时 | Electron 37.2.3 on 鸿蒙（**包内** Chromium 6584 文件 + Node 22.17.0） | ArkWeb（**系统**内核）+ 进程内 Node 24.2.0（`libnode.so`） | hos 有整套桌面 API 面；ark 必须 ArkTS 重写（§5 的 16 条） |
| ArkTS↔Node 通道 | adapter 桥，**真往返** ✅（`AppWindowAdapter#setTitle` in/out） | JSON 宿主桥，**传输层未接线** ✅（`host.js:109-115` 报 `transport-unavailable`） | ark 的 8 个宿主能力**已注册但不可达** |
| 服务形态 | 进程内 Next，绑 `0.0.0.0`＋密码＋Cookie 注入 | 进程内 Next，绑 `127.0.0.1`＋**免密**（`env.js` 路线 ①，`PiDesktopRuntime.ets:555`） | ark 更安全但**无局域网访问**；hos 反之 |
| 上游 | pi v1.2.0 / pi-web v0.12.1 + **2 补丁**（P203-1、PFIX-1） | pi-web v0.12.1 + **3 补丁**（PTY-1、CWD-1、CWD-2） | 补丁集**不重叠**：ark 缺 P203-1 Tab 形态与 PFIX-1 导出回退 |
| 包体 | HAP 370.8 MB | HAP **46.0 MB**（压缩后；载荷 tar.gz 另行 130 MB 级） | ark 的核心收益 |
| 自有 ELF | 无（用上游运行时归档）⇒ 不需二进制证书 | **有**（`libnode*.so`）⇒ 已用 `IGNORE_LIBRARY_VALIDATION` + 3 项 ACL ✅ | ark 多了合规工作，已处置 |
| 应用标识 | `Pi Desktop`（REV-2 品牌化） | **`Pi Desktop V2`**（`base/element/string.json:12-13`） | 上架前需定名 |

**一句话**：hos 把桌面 Electron 搬上鸿蒙；ark 用系统 WebView + 进程内 Node 重写桌面。
Electron 白送的一切（窗口/托盘/菜单/通知/协议/剪贴板/单实例）在 ark 里都是**待实现**，
反过来 ark 得到一个更小的包体、随机端口、可读的诊断面板，以及"不依赖子进程事件"的工具链。

## C. 清单外但 hos 有的能力（这 5 项才是"看起来该有却没有"的来源）

### C.1 ⛔ 会话导出 `/api/sessions/<id>/export` —— **确定性缺陷，且不能照抄 hos 的补丁**

| 项 | 内容 |
|---|---|
| hos 现状 | ✅ PFIX-1（`patches/v0.12.1/0002-session-export-in-process-fallback.patch`）已生效：200 + `text/html` + 300,444 B（进程内回退） |
| ark 现状 | ❌ **未打任何导出补丁** ⇒ 两条分支**都失败**（源码级判定，⬜ 未上真机） |
| 分支 1（spawn CLI） | `route.ts:218-221` 直接 `execFileAsync(process.execPath, [cliPath, "--export", …])`。ark 的 `process.execPath` = **`/system/bin/appspawn`**（`ohos-node-bridge/docs/能力矩阵.md` #19 ✅ 实测）。⚠️ **hos 的修复判据 `existsSync(process.execPath)` 在 ark 上恒为真**（appspawn 确实存在）⇒ 照抄 PFIX-1 **不会**回退，反而会真的去 spawn `appspawn` 并传 `--export` 参数 |
| 分支 2（进程内回退） | `route.ts:237` 的 `await import(exporterUrl)` **缺 `/* webpackIgnore: true */`** ⇒ 打包器改写成自己的模块查找 ⇒ `Cannot find module 'file:///…'`（hos 的实测现象，PFIX-1 第二个 hunk） |
| 结论 | 需要一条**新补丁**（暂记 `P-ark-4`），判据必须换成"当前进程是不是可用的 Node 运行时"，候选：`process.versions.electron` 为假 **且** `basename(process.execPath) === 'node'`；或直接用 `process.execArgv`/`process.report` 之类运行时自证。**判据先定，再谈回退** |
| 难度 | **低**（单文件、单函数、可幂等反向），但**判据必须重设计**，不是搬运 |

### C.2 ⚠️ `skills/harmony-runtime-capabilities` 技能包未随包

- hos：`scripts/collect-pi.mjs:384-390` 把 `skills/` 复制进 `resources/pi-agent/skills/`，首启物化到沙箱；
  该技能是 hos **唯一**的 #32 缓解手段（SKILL.md 明写 `**No command in bash is fenced.**`）。
- ark：`scripts/assemble-payload.mjs:101` 的 `APP_PAYLOAD_ENTRIES = ['pi-web-launch.js','env.js','extensions','config']`
  **不含 `skills`**；全仓库只剩 `payload/extensions/harmony-runtime.js:100` 一行**文字引用**该技能名。
- 后果：模型在 ark 上**不知道**平台限制（无 PTY、无围栏、`bash` 优先 read/write/edit、端口随机、日志通道），
  会更容易误用 `bash` 做本可以用 `read`/`edit` 完成的事。
- 难度：**低**（投放 + 文案按 ark 事实改写；不能直接搬 hos 的 SKILL.md，因为宿主不同）。

### C.3 ⚠️ 工作区选择器：4 个主目录 + Tab 形态

| 项 | ark 现状 |
|---|---|
| 根清单 | ⚠️ `payload/env.js#buildRoots` 会构造四项，但**兜底清单只有 sandbox**（用户目录需 OS 授权，`fallback:true` 机器可读标记） |
| 精确入口 | ✅ `GET /api/cwd/browse?root=sandbox`（CWD-1）已可用；hdc 视角路径由 CWD-2 归一为 el2 别名 |
| Tab UI | ❌ **无**。pi-web v0.12.1 的 `DirectoryPicker` 本身没有 tab 栏——那个 Tab 来自 hos 的 P203-1 补丁，本载荷未携带 |
| 结论 | 可达性目标达成（能直接选到工作区、不用手输），**形态不同**。若要 Tab，需移植 P203-1 的 UI 部分 |

### C.4 ⚠️ 局域网访问（远程打开 Pi Web）

- hos：`PI_WEB_HOSTNAME` = 局域网 IP + 随机密码 + Cookie 注入 ⇒ **可从 PC 浏览器访问**。
- ark：ArkTS 硬编码 `127.0.0.1`（`PiDesktopRuntime.ets:555`）；`payload/env.js:155-215` 的 `lan` 路线**已实现但未启用**
  （含 `0.0.0.0` 拒绝逻辑 F1）。
- 取舍：ark 的攻击面 = 同机其它应用（远小于绑 `0.0.0.0`），但少了"远程访问"这个用例。
  启用需要处理认证（密码 + ArkWeb Cookie 注入或会话 token）⇒ 难度中，安全面变大。

### C.5 ⚠️ 窗口状态记忆

- hos：`window-state.json`（尺寸/位置/最大化，含"是否可见于某显示器"的判据）。
- ark：❌ 全仓库**无 `@ohos.data.preferences` 引用** ⇒ 每次启动都是默认窗口。
- 难度：低-中（`window` API + `preferences`）；价值：低。

## G. 三条路线与建议（只给取舍，不排期）

| 路线 | 内容 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A 补齐"点了就坏"的可见缺口** | D2 导出 + D3 技能包 + D12 品牌名 + D13 取证 | 低（四项皆低/极低） | 导出不再 500；模型拿到平台约束技能；上架名称干净；关掉一个 ⬜ | 几乎为零（不触库、不触架构） |
| **B 打通 HostBridge 传输层** | D1 | **高** | 一次解锁 D5/D6/D7 + 优雅关停真能到达 Node | 触库 C 层 + 冻结契约面 ⇒ 需契约修订 + 一轮完整 review |
| **C 能力面继续对标** | D4 MCP + D8 Tab + D9 局域网 + D11 窗口状态 | 中 | 用法和 hos 一致；MCP 在 ark 上可行性高于 hos | D9 会放大攻击面；D10 价值低可跳过 |

**建议顺序：A → C（挑 D4、D8）→ B。**
理由：**A 的三项是确定性缺陷**（已能从源码判定必然失败，见 §C.1/§C.2），修完即可真机验证，不引入新风险；
**B 是唯一需要跨层改动的项**，应在 A/C 的实测反馈稳定后再动，避免"库 API 变更 + 消费方重写"两类风险叠加。
**D10（托盘/状态栏）建议不排期**：hos 自己也没做交互验收，且 pi-web 侧无消费点。
