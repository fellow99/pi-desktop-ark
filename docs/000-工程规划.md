> **一句话**：把 **Pi Desktop**（`pi-web` 前端 + `pi` agent）搬到 HarmonyOS：应用**自己的进程**里用

> 在 Node 里起 `pi-web` 服务端（同源 HTTP + SSE），主 UI 由 **ArkWeb** 渲染
> `http://127.0.0.1:<随机端口>/` —— **不带任何 Chromium/Electron**，功能**对标 `pi-desktop-hos`**。

## 1. 项目概述

### 1.1 一句话定义

`pi-desktop-ark` 是一个 **ArkTS 应用**：`EntryAbility` 启动时把库投进来，由库在**应用进程内**跑起 Node，
Node 里加载 `pi-web` 服务端（Next 16 运行时 + `pi` agent），监听 **loopback 随机端口**；
主界面是一个 **ArkWeb `Web` 组件**，它先显示应用内的加载页，探活成功后 `loadUrl('http://127.0.0.1:<port>/')`
加载**由本地服务渲染的**标准 Pi Web UI —— 同源、零 CORS、零 IPC、无头改写。

### 1.2 关键结论速览

| 维度 | 结论 | 出处 |
|---|---|---|
| 目标形态 | **无 Electron、无 Chromium**；Node 由库提供；主 UI 由 ArkWeb 渲染 | 本文 §4 |
| 与旧壳的关系 | 旧壳（Electron）**一次性退役**；`pi-desktop-hos` 只做**资产来源与对标基线** | §2、§8 |
| 数据面 | **沿用**「同源 HTTP + SSE」：`/`（SPA）、`/api/*`、SSE 直连本地服务 | §4 |
| ArkTS 宿主工作量 | **16 项能力**必须由 ArkTS 侧重实现（渲染、沙箱、端口探活、鉴权、窗口、外链、围栏、加载页、关停…） | §5 |
| 鉴权 | **首选 loopback 免密**（上游源码已证实 loopback 同源直通）；回退「局域网 + 密码 + Cookie 注入」 | §6 |
| 载荷 | **首选零解压**（`resfile/pi-web/` 只读直读）；可写缓存外置；可写入时才用 `tar.gz` + Node 自解包 | §7 |
| 载荷体积 | 现 `pi-dist` **884 MB / ≈27.2k 文件** → `tar.gz` **156.6 MB**；裁剪四项后**预估 70–90 MB**（⬜ 待实测） | §7.2 |

| 性能 | ✅ **已实证**：ACL 生效后 JIT 正常（热循环 **6–9 ms / 2e6**，约 **7–10×** 于解释器） | §10.3 |
| 上架合规 | 正面对上 AGC 的 ArkWeb 驳回项；**不打浏览器内核**；补齐 G1–G11 | §13 |

## 2. 背景：为什么必须换掉 `harmonypc-electron`

### 2.1 旧壳的结构性问题

`pi-desktop-hos`（旧壳）建立在 `harmonypc-electron` 之上：后端是 Electron 主进程里的 Node，前端是 Electron
`BrowserWindow` 里的 **Chromium**。它在真机上跑通了完整功能（✅ 旧壳 README：已签名真机验证），但有两个结构性问题：

1. **上架合规（刚性）**。同型工程 `dsh-desktop-hos` 被 AppGallery 以 **P0** 驳回，审核原文：
   > 「经检测发现，应用渲染打开网页时，未使用 ArkWeb 组件，不符合应用市场审核标准。」

   （🔶 原文见 `pi-desktop-hos/docs/工程规划.md:171`）该风险在旧壳里登记为最高风险 `R1`，并把「主 UI 迁移
   ArkWeb（R2）」列为**触发式目标**（🔶 同文档 `:299-314`、`:854`）。**本工程就是 R2 的落地形态**，
   而且更进一步：连 Chromium 本体都不再随包分发。
2. **随包分发浏览器内核**：`libelectron.so` 单件 **181 MB**（✅ `pi-desktop-hos/electron/libs/arm64-v8a/`），
   HAP 已签名产物 **320.3 MB**（🔶 旧壳文档 `:861`）。这部分体积换来的只是「渲染一个本地页面」。

⇒ 新形态必须同时做到「**无 Chromium**」与「**主 UI 走 ArkWeb**」；而 ArkWeb 只能加载 HTTP(S) 页面，
于是问题变成：**在没有 Electron、也没有可用子进程的前提下，如何把真正的 Node 塞进应用自己的进程** ——
这道题由 `ohos-node-bridge`（进程内 `dlopen` + `node::Start`）回答，见库文档 §4.6 路线 A。

### 2.2 旧架构的资产与负债

**必须重做的（Electron 面，✅ 逐行盘点见 §5）**：`app` / `BrowserWindow` / `Menu` / `screen` / `shell` /
`systemPreferences` / `session.cookies` / `webRequest.onBeforeSendHeaders` / `commandLine` 开关 /
`executeJavaScript` / `setWindowOpenHandler` / `will-navigate` / `before-input-event`。

**可以 100% 复用的（无 Electron 依赖，直接搬）**：

| 资产 | 位置 | 复用方式 |
|---|---|---|
| 进程内 Next 宿主（候选 A：`next/dist/server/lib/start-server.js`） | `pi-desktop-hos/src-main/main.js:601-736` | 原样搬进本工程的 Node 侧启动脚本（纯 Node 代码，与平台无关） |
| 流式 ustar 解包器（214 行状态机） | `pi-desktop-hos/src-main/tar-extract.js` | 搬进库的 bootstrap 载荷（仅当载荷走 `tar.gz` 路线时要） |
| 环境契约（`HOME`/`TMPDIR`/`PI_*`/`NO_PROXY`） | `pi-desktop-hos/src-main/main.js:237-307` | 搬进本工程启动脚本；`HOME`/`TMPDIR` 由库的 `env` 选项承载 |
| 三个同名工具扩展（`bash`/`find`/`grep`） | `pi-desktop-hos/extensions/harmony-{exec,search,runtime,workspace-roots}.js` | 原样随包，继续「同名顶替」 |
| 预置模板（`settings.json` / `mcp.json`） | `pi-desktop-hos/config/` | 原样 |
| 工作区目录补丁 + 权限桥消费点 | `pi-desktop-hos/patches/v0.12.1/0001-…patch` | 由库的宿主能力桥供数（§5 第 9/10 条） |

**可以直接删掉的（✅ 旧壳 1314 行主进程里属纯平台/纯体验项）**：`Menu.setApplicationMenu`、窗口状态记忆与
`screen.getAllDisplays`、F11/Alt+←、导出页返回按钮注入、`unsafely-treat-insecure-origin-as-secure`、
`proxy-bypass-list`、候选 B 子进程宿主（`main.js:739-816`，平台已知坏）。

### 2.3 目标负载对运行时的硬要求（✅ 均在本地源码/产物上核实）

| 要求 | 证据 | 对本工程的含义 |
|---|---|---|
| Node **`>=22.19.0`** | ✅ `pi/package.json:71`、`pi-web/package.json` `engines` | 库投放的 `libnode.so` 必须 ≥22.19（当前 v24.2.0 ✅） |
| Next.js **16.3.8**，**非 standalone**，进程内起服务 | ✅ `pi-web/package.json`；`pi-desktop-hos/src-main/main.js:601-736` | 载荷里必须有**完整**的 `node_modules`（或等价的可解析结构）；服务端必须是**同一进程**里的 Node |
| 设备侧 SWC 只能用 **WASM 版**（无 aarch64-ohos 原生件） | ✅ `pi-desktop-hos/pi-dist/node_modules/next/wasm/@next/` 存在；🔶 旧壳 `工程规划.md:859` R6 | **WebAssembly 是硬需求**；落点必须是 `node_modules/next/wasm/@next/swc-wasm-nodejs/` |
| 服务端 43 个编译产物引用 `child_process` | ✅ 盘点（`pi-dist/.next/server`） | 必须靠同名扩展顶替（`bash`/`find`/`grep`）或补丁；`spawn` 本机**完整可用**（库 §D.8），但设计仍不依赖其完成事件 |
| `fetch`（undici，含 `serverExternalPackages`） | ✅ `pi-web/lib/http-dispatcher.ts:5`、`next.config.ts` | undici 的 llhttp 是 **WASM** ⇒ 与 JIT 强耦合（库 §4.7） |
| `worker_threads`（pi SDK：图片缩放 / codemode QuickJS） | ✅ pi 侧依赖声明 | 运行时必须支持多线程；库不额外隔离（O3） |
| 模块格式 **CJS + ESM 混用** | ✅ `pi-dist/package.json` 无 `type`；`.next/package.json` = `commonjs`；`@earendil-works/*` = `module` | 需要 `require()` 失败退 `import()` 的加载器（旧壳已有） |
| 载荷规模 **884,167,367 B / ≈27.2k 文件** → `tar.gz` **156,592,393 B** | ✅ 本机 `du -sb` / `stat` | 就绪幂等判据必须存在；首启代价要可观测（🔶 旧壳首启到就绪约 15 s） |

### 2.4 平台事实来源

本工程**不重新论证**平台结论：进程内 `dlopen`+`node::Start` 的可行性与全部硬约束、notes 的六条硬约束、
`spawn` 的互斥证据与真机结论、`flock`/`link`/PTY/`git`/后台常驻等平台缺口、以及本机四条实测结论
（① 无 ACL SIGTRAP、①′ 开放权限不能替代、② `--jitless` 全绿但 WASM 全废、④ `--expose-internals` 可用）
**全部引库文档 §2.3 / §4 / §D.8**。

**本工程只需记住的使用面事实**（库 §D.8「实现偏差」原样继承）：

| 观察 | 值 | 对本工程的要求 |
|---|---|---|
| `dlopen` 路径 | **只有裸名 `libnode.so` 成功**；绝对路径全失败 | 库已按裸名 `dlopen`，本工程**不要**传路径 |

| `io_uring_setup(425)` | 返回 `8`（本机无 seccomp trap） | SIGSYS shim 属防御性保留，不是必需 |
| `uitest dumpLayout` | 本机拿不到结果 | 判据改用 HTTP 端点（`/facts` / `/log`）读回 |

## 3. 目标与原则

### 3.1 目标（对齐旧壳的「完整功能」，逐项见 §8.1）

1. **能起**：HAP 可安装启动，进入 Pi Desktop 窗口，**无白屏、无闪退**；
2. **能用**：Web UI 全功能可用 —— 会话列表/新建/重命名/导出、发消息、**流式（SSE）**、工具调用可视化、
   审批交互、上下文用量/成本、主题、多语言；
3. **能持久化**：会话落 `<filesDir>`（JSONL），重启应用后仍在；
4. **能配模型**：Settings › Models 可填 API Key / 登录，凭据落沙箱；
5. **能用工具**：文件读写/编辑/列目录、`bash`/`find`/`grep`（同名扩展）、工作目录选择与授权；
6. **能上架**：主 UI 由 ArkWeb 渲染、包内无浏览器内核、ELF 合规、许可齐备（§13）；
7. **失败可见**：任何一步失败都在 UI 上留下**可截图**的文字（加载页阶段 + 错误页 + 诊断面板），
   而不是白屏或静默。

### 3.2 设计原则

| 原则 | 展开 |
|---|---|
| **一切经 HTTP** | 前后端只通过同源 HTTP/SSE 通信；**不加 preload 桥、不引入 IPC 载体** |
| **壳薄、契约硬** | ArkTS 只做「启动 / 观测 / 宿主能力 / 渲染」，业务全在 Node 侧（与旧壳同一口径） |
| **不改上游** | 优先用现成机制（扩展、环境变量、同名顶替）；补丁必须**幂等、可反向**（§9） |
| **失败可见** | 状态机 + 阶段文本 + 日志尾上屏；崩溃是**终态**，明确提示「请重启应用」（库 §5.2） |
| **不隐藏平台真相** | 平台缺口如实上报（终端/`git`/后台/用户目录直写），**不静默降级** |
| **判据可证伪** | 每条验收都写成「能观测到 X」或「X 消失」，而不是「看起来好了」 |

**启动时序（失败可见）**

```
onCreate/onWindowStageCreate
  → 建窗 + 挂 ArkWeb（先在**应用内资源页** boot.html：显示阶段文本）
  → 申请所需权限（**必须在 loadContent 之后**，否则权限弹窗会卡启动屏 → APP_INPUT_BLOCK）
  → NodeRuntime.start()（立即返回）→ 轮询状态：starting → running
  → 探活 http://127.0.0.1:<port>/（退避重试；失败立刻回退到错误页，不等满超时）
  → loadUrl('http://127.0.0.1:<port>/')  → 成功则 clearHistory()
  → 失败/崩溃：错误页 + 日志尾 + 「重启应用」提示（进程内 Node 不可重启）
```

## 6. 鉴权与安全边界

### 6.1 上游源码事实（✅ 直接核实，库文档 §6.3 同源）

- `pi-web/lib/web-auth.ts:15-19`：`isWebPasswordEnabled()` = `PI_WEB_PASSWORD` 非空。**未设密码 ⇒ 认证整体关闭**；
- `pi-web/proxy.ts:42-47`：未启用密码时，只要通过 Host 围栏就直接 `NextResponse.next()`；
- `pi-web/lib/request-security.ts:90-102`：`isApiRequestHostAllowed()` 对 **loopback 主机名或 IP 字面量直接放行**
  ⇒ 同源请求天然通过，**不需要头改写**（这是本工程比同型工程少一套补丁的原因）；
- `pi-web/proxy.ts:50-70`：启用密码后，**会话 cookie 优先** —— `isValidWebSessionToken(cookie)` 对**包括 `/api/*` 在内**
  的所有请求生效；Basic 头只是**额外**的一条路径。

### 6.2 两条路线

| 路线 | 做法 | 前置条件 | 代价 |
|---|---|---|---|
| **① loopback 免密（首选）** | 服务端只监听 `127.0.0.1:<随机端口>`，**不设** `PI_WEB_PASSWORD`；ArkWeb 加载 `http://127.0.0.1:<port>/` | 🔶 同形态先例**已在售**：ArkWeb `loadUrl('http://127.0.0.1:5577')`（✅ 源码级证据，库 §5.10 第 6 条）；本工程仍需 P0-3 自测 | 无认证（本机进程内，攻击面 = 同机其它应用，比绑 `0.0.0.0` 小得多）；安全上下文大概率成立 |
| **② 局域网 + 密码 + Cookie 注入（回退）** | 绑 `0.0.0.0`，`PI_WEB_HOSTNAME` = 局域网 IP，宿主生成随机密码；Node 侧用同算法派生 `pi_web_session`（`v1.<exp>.<nonce>.<HMAC-SHA256(密码)>`），ArkTS 用 ArkWeb 的 Cookie 管理写入 | ⬜ ArkWeb Cookie 注入 API 可用（P0-3） | 需要 cookie 注入；局域网暴露面（随机端口 + 强密码缓解） |

**两条路线都**：不改上游、不加 preload 桥、不引入 IPC 载体。

### 6.3 端口与单实例（硬约束 ⑰，✅ 已实测）

⚙️ 实测：15577 被别的应用占用时启动本应用 → 载荷 `server.listen()` 抛 `EADDRINUSE` → **进程内 Node 的未捕获异常
把整个 App 进程 abort**（`Cpp Crash`，崩溃栈含 `libnode_bridge.so`）；腾出端口后同一构建完全正常
（见 [`docs/ACL配置.md`](ACL配置.md) §3.1、库文档 §D.10）。

⇒ 本工程必须：**端口随机（或先探测空闲）** + **`launchType: singleton`** + **载荷自装异常兜底**（⑱）；
且 Node 侧的日志要求「谁写谁读」：载荷把错误写进**自己的**日志通道（`payload/app.log`），不要只依赖 stdout
（库的 `dup2` 会把 ArkWeb 原生输出混进同一份 `node.log`）。

### 10.2 三项 ACL（受限权限，按本包名申请）

| # | 权限 | 用途 | 判定 |
|---|---|---|---|
| 1 | `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | 进程内 Node/V8 的 **JIT**（无它 V8 走 JIT 即 SIGTRAP，属应用级失败） | `system_basic` + `provisionEnable=true` ⇒ 需 ACL |
| 2 | `ohos.permission.READ_PASTEBOARD` | 剪贴板文本/图片粘贴到对话输入框 | 同上 |
| 3 | `ohos.permission.READ_WRITE_DESKTOP_DIRECTORY` | 工作目录位于桌面目录时 agent 文件工具直写 | 同上 |

**申请正文（≤256 字，可直接粘贴进 AGC「ACL 权限」页签）**：

> 本应用在自身进程内嵌 Node.js（V8）运行时以提供本地 AI 助手与本地服务，V8 的基线编译与优化编译
> （Maglev/TurboFan）必须创建可执行内存页。经真机验证：未授予该权限时，应用在启动运行时的瞬间即因 W^X 策略
> 触发 SIGTRAP 崩溃（`si_addr == pc`，系统判定 Cpp Crash）；声明 `kernel.EXEMPT_ANONYMOUS_EXECUTABLE_MEMORY`
> 等开放权限无法替代。本应用不使用 WebView 之外的浏览器内核，不加载外部可执行文件，仅使用平台官方提供的
> 可执行内存能力。
