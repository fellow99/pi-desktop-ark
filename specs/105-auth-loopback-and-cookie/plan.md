## 3. 研究结论（决策 / 替代方案 / 为何否掉）

| 编号 | 决策 | 替代方案 | 为何否掉 |
|---|---|---|---|
| `D-105-1` | **路线 ① 为默认**（只监听 loopback + 不设密码） | 一律启用密码（「更安全」的直觉方案） | 上游源码事实：未设密码时认证整体关闭（✅ `web-auth.ts:15-19`），且 loopback 请求由 Host 围栏直接放行（✅ `request-security.ts:97`）⇒ 启用密码只是**多加一道必须自己喂凭据的闸门**，同时把接口暴露面从「同机」扩到「局域网」（绑 `0.0.0.0`） |
| `D-105-2` | 回退路线**必须**同时具备：绑所有网卡 + 对外主机名 + 随机强密码 + 会话凭据注入 | 只绑局域网但不设密码 | 等于把无认证的助手接口交给局域网；攻击面不可接受 |
| `D-105-3` | **不**注入 `Authorization: Basic` 头 | 沿旧壳做法「cookie + Basic 双注入」 | 旧壳注入 Basic 是为 `webRequest.onBeforeSendHeaders`（Electron 面）；**本工程无头改写能力**（宪法 A1 禁），且首屏（非 API 路径）**只认 cookie**（✅ `proxy.ts:50-70`）⇒ Basic 对本形态没有增益，只增加凭据暴露面 |
| `D-105-4` | 凭据经**文件**传给壳（`payload/session.json`） | 经宿主能力桥传；或壳自己派生 | 桥传凭据违反 A2/A1 分工与「桥只承载能力调用」；壳自己派生要把密码也交给壳 ⇒ 密码出现在两处。文件是本工程既有的「Node → 壳」通道形态（与 `payload/port` 同族） |
| `D-105-5` | 就绪探针用**恒定放行**端点（上游 `/api/web-auth`） | 探 `/` | 启用密码时 `/` 会 302 到登录页（不是 200）；探针与真实判据不一致正是当前骨架的缺陷（`TC-101-002` 现状不通过） |
| `D-105-6` | 密码**每启随机**、长度 32 字节（base64url 43 字符） | 固定密码 / 用户手输 | 固定密码必然进日志与文档；手输破坏「首屏直达」（`FR-ARK-009`）。🔶 旧壳同口径（`main.js:705-717`） |
| `D-105-7` | **不做**任何上游补丁（登记 `P-ark-1` 为「优先不补」） | 给上游加一条「允许 loopback 免密」的补丁 | 上游**本来**就这样（两条源码事实）；补丁只会制造漂移风险（宪法 A4） |
| `D-105-8` | **禁止** `PI_DESKTOP_PASSWORD` 式固定密码变量进发布物 | 保留下载调试便利 | 🔶 旧壳明确警告它会出现在环境变量与日志里；上架红线 G9 |

## 4. 数据模型（真实字段 / 配置矩阵 / 校验规则）

### 4.1 会话凭据（cookie）结构与生成算法

| 项 | 值 / 规则 | 依据 |
|---|---|---|
| Cookie 名 | `pi_web_session` | ✅ `web-auth.ts:4` |
| 值形态 | `v1.<exp>.<nonce>.<sig>`（四段，`.` 分隔） | ✅ `web-auth.ts:60-67` |
| `exp` | `floor(now/1000) + 2592000`（签发时刻 + **30 天**，十进制秒） | ✅ `web-auth.ts:5`（`PI_WEB_SESSION_MAX_AGE = 60*60*24*30`）、`:65` |
| `nonce` | 16 字节随机 → 32 位小写 hex | ✅ `web-auth.ts:63` |
| 签名消息 | `pi-web-session:` + `v1.<exp>.<nonce>`（即 payload 原文） | ✅ `web-auth.ts:56-58` |
| `sig` | `HMAC-SHA256(key = 访问密码, msg = 签名消息)` 的小写 hex（**64 位**） | ✅ `web-auth.ts:57` |
| 上游接受条件 | 正则 `^(v1\.(\d+)\.[a-f0-9]{32})\.([a-f0-9]{64})$` 且 `exp > now` 且签名比对通过 | ✅ `web-auth.ts:76-81` |
| Cookie 属性（写入组件时） | `path='/'`、`httpOnly=true`、`sameSite='lax'`、`maxAge=2592000` | 🔶 旧壳 `main.js:897-904`（本工程未复现） |
| Basic 用户名（仅诊断参考，本工程不注入） | `pi` | ✅ `web-auth.ts:3` |

**生成伪码（Node 侧，仅回退路线执行）**

```
password = base64url(randomBytes(32))            # 43 字符；每启新值
exp      = floor(Date.now()/1000) + 2592000
nonce    = randomBytes(16).toString('hex')
payload  = `v1.${exp}.${nonce}`
sig      = hmac_sha256(password).update(`pi-web-session:${payload}`).hex()
value    = `${payload}.${sig}`
```

### 4.2 两条路线的配置矩阵（环境变量级）

| 变量 | 路线 ①（默认） | 路线 ②（回退） | 说明 |
|---|---|---|---|
| `PI_WEB_PASSWORD` | **不设** | 43 字符随机串（不落日志） | 不设 ⇒ 上游认证整体关闭（✅ `web-auth.ts:15-19`） |
| `PI_WEB_HOSTNAME` | **回环值**（并行落地的 `env.js:146` 设为 `127.0.0.1`；`overall-data-model.md` §3 的「不设」按「**不对外**」理解） | **本机真实可达地址**（从设备网络事实取，**不得**猜；⚠️ 落地代码 `env.js:140` 在缺 `lanIp` 时兜底 `0.0.0.0`，须改为显式要求） | 上游用它做 Host 白名单（`request-security.ts:99-101`） |
| `PI_WEB_PORT` | **不指定固定端口**（并行落地的 `env.js:148` 送 `0` ⇒ 由服务随机取） | 同左（`env.js:141`） | 硬约束 ⑰；实际端口经 `101` 的通道回传 |
| 服务监听地址 | 仅回环 | 所有网卡 | 由载荷的 `listen(...)` 决定（属 `102`） |
| `NO_PROXY` / `no_proxy` | 追加 `127.0.0.1,localhost` | 追加 `127.0.0.1,localhost,<对外地址>` | 🔶 旧壳 `main.js:276-281` |
| `PI_DESKTOP_PASSWORD` | **不设**（**禁止**引入） | **不设** | `D-105-8`；G9 |
| `PI_WEB_SKIP_VERSION_CHECK` / `PI_WEB_APP_NAME` | 相邻项（品牌化，⬜ 定稿） | 同左 | 由 `101` 的 env 装配统一负责；本模块只登记**不得**与之冲突 |

### 4.3 凭据传递载体文件

| 项 | 值 |
|---|---|
| 路径 | `<filesDir>/payload/session.json`（绝对路径；`payload` 目录由 `101` 保证存在） |
| 内容 | `{"v":1,"cookieName":"pi_web_session","value":"<凭据>","origin":"http://127.0.0.1:<port>/","at":<epochMs>,"route":"loopback\|lan"}` |
| 写入方式 | **原子写**（临时文件 + `rename`；🔶 沙箱 `hmfs` 支持原子写） |
| 权限 | 写入后 `chmod 0600`（🔶 沙箱 `hmfs` 如实回读权限） |
| 读取方 | ArkTS 注入模块（`shell/AuthSession.ets`） |
| 失效规则 | `route`/`origin` 与实际目标不一致 ⇒ **丢弃并报告**（不得把过期凭据当有效） |
| 卫生 | 该文件**不得**被日志打印、**不得**进入崩溃记录、**不得**进入任何导出物 |

### 4.4 校验规则

1. **路线决定**：路线 ① 的判据是「服务只监听回环 + 密码变量为空」；任一不成立 ⇒ 视为路线 ② 或配置错误（必须报错，不静默）。
2. **证书形态**：四段 + 版本 `v1` + `exp > now` + `nonce` 32 hex + `sig` 64 hex（与上游正则一致；本模块实现里写成**同一正则**并以注释标注上游出处）。
3. **注入目标**：`origin` 必须与首屏地址完全一致（scheme/host/port 三项），否则注入无意义。
4. **失败分级**：`auth-route-mismatch`（配置矛盾）/ `token-file-missing` / `token-invalid` / `cookie-write-failed` —— 四类各自给文案（`FR-105-017`）。

### 5.3 事件协议（启动顺序，注入必须在加载之前）

```
[Node 侧] 装配 auth env（§4.2）→ 起服务（listen 回环/所有网卡）
        → 路线 ② 时：生成密码 → 派生凭据 → 原子写 <filesDir>/payload/session.json
        → 就绪后把实际端口回传（101 通道）
[壳 侧] 探活 /api/web-auth（恒定放行）→ READY
        → 读 session.json（路线 ②）→ injectSessionCookie(origin)
        → 成功 ⇒ loadUrl('http://127.0.0.1:<port>/')
        → 失败 ⇒ FAILED + 「凭据注入失败」文案 + 「请重启应用」三动作菜单（A5）
```

- 路线 ①：`injectSessionCookie` 返回 `skipped`，**不**读文件、**不**注入（免密形态下无凭据）；
- **禁止**在 `loadUrl` 之后再注入（首屏会先跳登录页）；
- 凭据**不得**出现在任何日志行（只允许记长度、路线、`origin`）。

## 6. 实现策略

### 6.1 架构模式

- **路线是一个显式配置**（`loopback | lan`），由「服务监听范围 + 密码变量是否存在」共同决定，**任何**不一致必须报 `auth-route-mismatch`；
- Node 侧只做**装配与派生**（无状态、幂等：重复调用生成新凭据并覆盖文件）；
- 壳侧只做**读文件 + 注入 + 失败上屏**，不含任何密码学运算。

### 6.2 关键算法与失败处理

| 场景 | 处理 |
|---|---|
| 路线 ①（默认） | 不设密码/主机名/端口变量；`NO_PROXY` 追加 `127.0.0.1,localhost`；探 `/api/web-auth` 200 ⇒ READY ⇒ 直接 `loadUrl` |
| 路线 ① 被证伪（P0-3 失败） | 记录截图证据 → 切路线 ② → 装配对外主机名（设备网络事实）+ 随机密码 → 派生凭据 → 壳注入 ⇒ 首屏无登录页 |
| 注入失败 | **不**把登录页当正常界面；状态机 `FAILED` + 文案「认证凭据注入失败（原因）」+ 「重试 / 查看日志 / 重启应用」（宪法 A5 三动作） |
| 凭据文件缺失/失效 | `token-file-missing` / `token-invalid` → 同上传失败路径；**不得**回退到「无凭据试一下」 |
| 代理拦截 | `NO_PROXY` 追加后仍失败 ⇒ 文案指出「疑似代理拦截本机请求」（属可归因，不是静默） |

### 6.3 性能与安全

| 面 | 纪律 |
|---|---|
| 派生 | 一次 HMAC-SHA256 + 一次随机（微秒级）；**不得**引入常驻线程/定时器 |
| 文件 | 一次性原子写（≤ 1 KiB）；**不得**读回打印 |
| 时序 | 注入 + 探活在 READY 阶段完成，**不**引入额外网络往返（路线 ① 下零凭据） |
| 卫生 | 明文密码与凭据只存在于：Node 进程内存、`session.json`、组件 Cookie 存储；**不得**出现在日志/系统日志/崩溃记录/导出物 |
